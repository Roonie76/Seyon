# Seyon — Adversarial Pre-Launch Audit

**Date:** 23 August 2026
**Scope:** Full repository (266 tracked files), executed against a live instance
**Method:** Static review + a running instance (PostgreSQL 16, seeded, `next dev` *and* a production `next build && next start`), Playwright multi-context browser testing, direct server-action invocation over HTTP, and direct SQL verification of database state after every mutation.

Every finding below is labelled **Confirmed** (reproduced against the running app), **Verified by code path** (the defect is unambiguous in code but the external dependency needed to execute it — live Supabase — was not available), or **Architectural concern**.

---

## 1. Executive summary

Seyon's MVP is further along than most pre-launch codebases. Authorization on product CRUD is genuinely solid — every IDOR attempt I made was correctly rejected server-side. There is no stored XSS. Field-level updates do not clobber neighbouring fields. Cascade deletes leave no orphan rows. Pagination produces no duplicates or gaps. WhatsApp verification is properly built (CSPRNG codes, hashed at rest, expiry, attempt caps, rate limits). The existing suite of 100 tests passes and `tsc --noEmit` is clean.

That is the good news, and it is real.

The bad news is that **the failure modes that remain are the expensive kind**: they are silent, they are reachable through the normal product-creation flow, and several of them affect *other people's* data or the shared marketplace rather than only the actor's own account.

The four that should block launch:

1. **Fabricated social proof renders in production.** A shop with zero reviews and no city is displayed to buyers as `⭐ 4.8 (100)`, tagged *"Verified Creator"*, located in *"Mumbai"*. The `demo.ts` guardrail is real, but page components bypass it with their own inline fallbacks (`shop.reviewCount || 100`) and one hard-coded `⭐ 4.9 (124 reviews)` in the homepage hero. Reproduced in a production build.
2. **Any seller can 500 the public homepage.** A product image URL whose host is not in `next.config.ts remotePatterns` — accepted by the create-product API, which validates only that the string is a URL — makes `next/image` throw during render. The homepage returns HTTP 500 for every visitor, and the seller's own product dashboard becomes unusable. Reproduced; confirmed by removing the row and watching the homepage recover.
3. **Concurrent edits silently lose data.** Two tabs editing the same product each send the whole record; the second write wins and both report success. Reproduced: tab A's price change vanished while both dialogs said "Product updated successfully".
4. **A double-click creates a duplicate product.** The submit button is re-enabled the moment the server responds, while the success dialog stays open for another 1.2 seconds. Reproduced: one logical action, two database rows.

Underneath those sits a systemic error-handling gap: **not one server-action call in the app is wrapped in `try/catch`**. On any network blip, cold-start timeout or 500, the UI freezes on a disabled "Creating Product…" button with no message and no retry — reproduced by aborting the request mid-flight.

Nothing here requires re-architecting. The fixes are small and local. But shipping without them means the first week of real traffic produces duplicate listings, lost edits, mysterious frozen forms, and — the one that is hardest to walk back — review counts and ratings on the storefront that nobody can substantiate.

**Verdict: not ready to launch today; roughly one focused week of fixes away.**

## 2. Critical findings

### F-01 — Fabricated ratings, review counts, locations and trust badges render in production
**Severity: P0 · Confirmed (production build)**

**Location**
`src/app/(shopper)/page.tsx:696`, `:921`, `:1280` · `src/app/(shopper)/creators/page.tsx:108`, `:115`, `:118` · `src/lib/demo.ts:98-107`

**Steps to reproduce**
```bash
NODE_ENV=production npx next build && npx next start
# create a shop with no reviews, no city, isVerified = false
curl -s http://localhost:3001/creators | grep -A2 "Audit Shop"
```

**Expected** A shop with no reviews shows no rating, no review count, no location it never entered, and no verification claim.

**Actual** Rendered production HTML for a brand-new shop:

| Rendered | Real value |
|---|---|
| `⭐ 4.8` | `averageRating = 0` |
| `(100)` reviews | `reviewCount = 0` |
| `Verified Creator` | `isVerified = false` |
| `Mumbai` | `city = null` |

The homepage hero additionally carries a literal `⭐ 4.9 (124 reviews)` (`page.tsx:696`) that is rendered for whatever product occupies the slot. `"Verified Creator"` appeared 12 times in a single production homepage render.

**Root cause** `src/lib/demo.ts` correctly gates its fabrications behind `NODE_ENV === 'development'` — but its *production* branch still returns `rating: 4.8` and `location: 'Mumbai'` as defaults (`baseRating`/`baseLocation`, lines 98-99) and a blanket `trustTag: 'Verified Creator'` (line 105). Independently, the page components add their own fallbacks the demo module never sees: `({shop.reviewCount || 100})`.

**Recommended fix** Make `CreatorPresentation` fields nullable and render nothing when the underlying value is absent. Delete the `|| 100` fallbacks and the hard-coded hero rating. Derive the trust tag from `isVerified` / `whatsappVerifiedAt`. Guarded by `tests/regression/demo-isolation.regression.ts`.

> This is also the highest *non-technical* risk in the report: displaying an invented review count is a consumer-protection exposure, not just a bug.

### F-02 — One product row can return HTTP 500 for the entire public homepage
**Severity: P0 · Confirmed**

**Location** `src/shared/lib/zod-schemas.ts:37` (`ProductImageSchema.url`) · `next.config.ts:35-46` · every `<NextImage>` render site

**Steps to reproduce**
```js
// authenticated as any seller, via the normal createProduct server action
createProduct(shopId, { title:'x', price:1, category:'Other',
  images:[{ url:'http://127.0.0.1:5432/', isPrimary:true, displayOrder:0 }] })
```
Then `curl -o /dev/null -w '%{http_code}' http://localhost:3001/`

**Expected** The bad image degrades to a placeholder; the page renders.

**Actual**
```
GET /          → 500        (whole homepage down, for every visitor)
GET /dashboard/products → "Something went wrong" (seller locked out of ALL their products)
GET /marketplace, /store/…, /category/… → 200 but the card is replaced by an error boundary
```
Server log: `Error: Invalid src prop (http://127.0.0.1:5432/) on 'next/image', hostname "127.0.0.1" is not configured under images`.

Deleting the two offending rows restored `GET /` to 200 — causality confirmed.

**Root cause** `ProductImageSchema` accepts any syntactically valid URL of any scheme and host (`javascript:alert(1)` was accepted too). `next/image` throws — not warns — on an unconfigured host, and the throw is not contained by a per-card error boundary on the homepage.

**Recommended fix** Two independent layers, both needed:
1. Constrain `ProductImageSchema.url` to `https:` plus the exact hosts in `remotePatterns` (reject private/loopback/link-local addresses while you are there — see F-05).
2. Wrap each product card in an error boundary, or use `unoptimized`/`onError` fallbacks so one bad row cannot take a shared page down.

Also worth noting: this fires without any attacker. Change the storage host, migrate buckets, or inherit one legacy URL, and the homepage goes down.

### F-03 — Double-clicking "Deploy Listing" creates a duplicate product
**Severity: P1 · Confirmed**

**Location** `src/frontend/components/dashboard/product-manager.tsx:214-240`

**Steps to reproduce** Fill the Add Product dialog → click *Deploy Listing* → the moment "Product created successfully!" appears, click it again.

**Actual**
```
action requests fired: 2
DB rows: [ {slug:'double-click-product'}, {slug:'double-click-product-1'} ]
```

**Root cause**
```ts
setIsLoading(false);          // ← button re-enabled here
if (res.error) { … } else {
  setMessage({ type:'success', … });
  setTimeout(() => { …; window.location.reload(); }, 1200);   // dialog open another 1.2s
}
```
There is a 1.2-second window in which the form is armed and the success message is already showing — the exact moment an impatient user clicks again.

**Recommended fix** Keep `isLoading` true on the success path (only clear it in the error branch), or set a separate `submitted` flag that also disables the button. Guarded by `tests/e2e/audit-regression.spec.ts` (F-03).

### F-04 — Concurrent edits silently overwrite each other (lost update)
**Severity: P1 · Confirmed**

**Location** `src/backend/actions/products.ts:160-302`

**Steps to reproduce** Two tabs open the same product. Tab A changes price to 999. Tab B changes the description. Both save.

**Actual**
```
A: {"success":true}     B: {"success":true}
final DB: { price: 100, description: "NEW DESC from B" }   ← A's price change is gone
```
Both users were told their change was saved. Neither is told anything was overwritten.

**Root cause** `updateProduct` accepts the full `ProductSchema` and writes every field unconditionally. There is no version column, no `updatedAt` precondition, no field-level patching. Last writer wins, whole-record.

**Recommended fix** Minimal change that preserves the current architecture: send the product's `updatedAt` from the client and make the write conditional —
```ts
const res = await tx.product.updateMany({
  where: { id, updatedAt: expectedUpdatedAt },
  data: { … },
});
if (res.count === 0) return { error: 'This product was changed in another tab. Reload and try again.' };
```
Same treatment for `updateShop`.

### F-05 — Server-side SSRF via product image URLs
**Severity: P1 · Confirmed (outbound request observed)**

**Location** `src/backend/actions/products.ts:100`, `:231`, `:336`

**Steps to reproduce** Run a listener on `127.0.0.1:9911`, then create a product with `images[0].url = 'http://127.0.0.1:9911/internal-secret?x=1'`.

**Actual** The listener logged `HIT GET /internal-secret?x=1 ua=node` — the Seyon server made the request.

**Root cause** All three creation/update paths do `await fetch(userSuppliedUrl)` for colour extraction, with no scheme, host, or IP-range restriction.

**Impact** Blind SSRF from the deployment's network position: internal service probing, cloud metadata endpoints, and port scanning by response timing. Any authenticated seller can trigger it.

**Recommended fix** Only fetch URLs matching the configured storage host (the same allowlist as F-02). If arbitrary hosts must ever be supported, resolve the DNS name first and reject private/loopback/link-local addresses.

### F-06 — Image fetch and decode have no timeout, no size cap, and leak an unhandled rejection
**Severity: P1 · Confirmed**

**Location** `src/backend/actions/products.ts:99-111` · `src/backend/lib/color/extractDominant.ts`

**Steps to reproduce** Create a product whose image URL returns a truncated/malformed PNG.

**Actual**
```
POST /dashboard/products 200 in 115s
⨯ unhandledRejection: Error: End-Of-Stream
```
A single malformed image blocked the server action for **115 seconds** and produced an unhandled promise rejection that escaped `extractDominantColor`'s own `try/catch` (node-vibrant rejects from an internal stream, outside the awaited promise).

**Impact** On Vercel this exceeds the function timeout: the seller waits, then the request dies. Combined with F-08 the dialog then freezes forever. The unhandled rejection can terminate the Node process depending on runtime configuration. A slowloris URL turns this into a cheap DoS.

**Recommended fix** `fetch(url, { signal: AbortSignal.timeout(5000) })`; cap the response body (reject over ~5 MB); wrap the whole colour step in `process`-safe handling; and — best of all — move theme extraction out of the request path entirely (do it at upload time or in a background job). Colour extraction should never be able to fail a product creation.

### F-07 — Non-Latin and blank titles produce empty or degenerate slugs
**Severity: P1 · Confirmed**

**Location** `src/backend/actions/products.ts:19-27` (`slugify`) · same logic duplicated in `store-forms.tsx:78-88`

**Steps to reproduce** Create products titled `மணிமாலை நகை`, `🌸🌸🌸`, and `"   "`.

**Actual**
| Title | Stored slug | Result |
|---|---|---|
| `"   "` (spaces) | `""` | `/store/audit-shop/` → **renders the store page, not the product**. The product is unreachable and its link silently points at the wrong page. |
| `மணிமாலை நகை` | `"-"` | URL is a bare hyphen |
| `🌸🌸🌸` | `"-1"` | collision-suffixed hyphen |

**Root cause** `.replace(/[^\w\-]+/g, '')` — `\w` is `[A-Za-z0-9_]`, so every Tamil, Devanagari, Bengali, Arabic or CJK character is deleted. Every all-Indic title in a shop collapses into the same `-`, `-1`, `-2` namespace. `z.string().min(2)` also lets `"  "` through because it does not trim.

**Impact** For a marketplace aimed at Indian creators this is not an edge case — it is the expected input. Product pages become unreachable, share links break, SEO is destroyed for those listings.

**Recommended fix** `.trim()` and a non-empty check in `ProductSchema`; transliterate or percent-encode non-ASCII (or fall back to `product-${cuid}` when the slug would be empty); keep the two `slugify` copies in one shared module.

### F-08 — Every failed mutation leaves the UI permanently stuck, with no error shown
**Severity: P1 · Confirmed · Systemic**

**Location** `product-manager.tsx:214`, `:243`, `:255` · `store-forms.tsx:61`, `:377`, `:321`, `:335` · `store-client-buttons.tsx:76`, `:172`

**Steps to reproduce** Fill the Add Product dialog, abort the POST mid-flight (`route.abort('connectionfailed')`), submit.

**Actual**
```
[pageerror] Failed to fetch
submit button: "Creating Product..."  disabled = true
error banner: none
DB rows: none
```
The seller is left staring at a disabled spinner. There is no message, no retry, and reloading loses the entire form including the uploaded images.

**Root cause** The pattern is identical in nine places:
```ts
setIsLoading(true);
const res = await someServerAction(...);   // ← no try/catch
setIsLoading(false);                       // ← never runs if the promise rejects
```
Server actions reject on network failure, 500s, and function timeouts (see F-06) — all of which are routine in production.

**Recommended fix** Wrap each call in `try/catch/finally`, reset loading in `finally`, and surface a retryable error. This is nine small edits and it is the single highest-value change in the report for perceived reliability.

### F-09 — Storage misconfiguration silently substitutes stock photos and reports success
**Severity: P1 · Verified by code path**

**Location** `src/backend/lib/supabase.ts:14-26`

```ts
if (supabaseUrl.includes('mock-project') || !process.env.SUPABASE_URL) {
  return `https://images.unsplash.com/photo-1505740420928-…&mock=${randomId}`;
}
```

**Impact** There is **no environment gate**. If `SUPABASE_URL` is missing or misspelled in the Vercel project, uploads return HTTP 200 with a random Unsplash stock photo, the seller sees "success", and the catalogue quietly fills with images of products nobody sells. Discovering this after launch means auditing every image in the database. `deleteFile` no-ops on the same condition, so cleanup silently does nothing too.

**Recommended fix** Gate the mock branch on `NODE_ENV !== 'production'` and throw a startup error when `SUPABASE_URL` is absent in production.

### F-10 — Cross-tenant image deletion
**Severity: P1 · Verified by code path (live Supabase not available to execute)**

**Location** `src/backend/actions/products.ts:206-214`, `:433-436` · `src/backend/lib/supabase.ts:62-82`

**Attack** `deleteFile` derives the storage path from whatever URL it is given and issues an unconditional `storage.remove()` — no ownership check, and buckets share a flat namespace. Image URLs on a product are fully attacker-controlled:

1. Read a competitor's public product page; copy their image URL.
2. Create your own product with that URL in `images[]` (accepted — see F-02/F-05).
3. Delete your product. `deleteProduct` loops over `product.images` calling `deleteFile(img.url, 'products')`.
4. The competitor's image file is gone from storage; their listings show broken images with no way to tell what happened.

The same primitive exists in `updateProduct` (add the victim's URL, save, remove it, save again).

**Recommended fix** Before deleting, confirm the storage object is referenced only by rows belonging to this shop — or (simpler and stronger) prefix uploads with the shop id and refuse to delete any path outside the caller's prefix.

### F-11 — Passwordless dev login is active in production builds
**Severity: P1 (P0 if the flag is ever set on the live project) · Confirmed**

**Location** `src/backend/lib/dev-login.ts` · `src/backend/lib/auth.ts:37-81` · `.env.local`

The comment says *"Excluded from production builds"*. It is not — `isDevLoginEnabled()` checks only `ALLOW_INSECURE_DEV_LOGIN === 'true'`. Started under `next start` with `NODE_ENV=production`, the app logged:

```
SECURITY WARNING: Insecure dev login credentials provider is active!
```

…and passwordless sign-in worked. The repository's own `.env.local` contains `ALLOW_INSECURE_DEV_LOGIN="true"`. Anyone who reaches a deployment with that flag can sign in as **any email address with no password**, including `admin@seyon.com`, which grants full admin.

**Recommended fix** `return override === 'true' && process.env.NODE_ENV !== 'production';` and verify the variable is absent from every Vercel environment before launch. Fix the misleading comment.

### F-12 — The upload route depends on an undeclared package
**Severity: P1 · Confirmed (dependency graph)**

**Location** `src/app/api/upload/route.ts:46-50`

`await import('file-type')` — but `file-type` is **not in `package.json`**. It resolves only because npm hoists it out of `@jimp/core` → `node-vibrant`. The code even anticipates the failure (`throw new Error('file-type fromBuffer is not a function')`), which is what happens with any modern `file-type` (v17+ is ESM and exports `fileTypeFromBuffer`, not `fromBuffer`).

**Impact** A `node-vibrant` bump, an npm dedupe change, or a switch to pnpm/yarn PnP breaks **all image uploads** with a 500 — the core seller workflow — with no test covering it.

**Recommended fix** Add `"file-type": "^16.5.4"` to `dependencies` (or migrate to the modern API), and add a smoke test for `POST /api/upload`.

### F-13 — `prisma db seed` truncates every table, and the dev `.env` points at production
**Severity: P1 (operational) · Confirmed by inspection**

**Location** `prisma/seed.ts:8-16` · `package.json` (`prisma.seed`) · `.env`

`main()` opens with `deleteMany({})` on Analytics, Report, Review, ProductImage, Product, Shop, BlogPost and **User**. The repo's `.env` sets `DATABASE_URL` to a live Supabase instance. One `npx prisma db seed`, one `prisma migrate reset`, one IDE "run seed" button — and production is empty.

**Recommended fix** Refuse to run when the target URL is not localhost (or require `SEED_CONFIRM=<database name>`). Point local development at the docker-compose Postgres that already exists in the repo.

### F-14 — Analytics are publicly writable and inflated by bots
**Severity: P1 · Confirmed**

**Location** `src/backend/actions/analytics.ts:12-23` (`trackEvent` is an exported server action) · `store/[shopSlug]/[productSlug]/page.tsx:93`

Two separate problems in the same data:

**Forgeable.** `trackEvent(shopId, eventType, productId)` is an exported server action with **no authentication, no ownership check and no rate limit**. Anyone can write unlimited `SHOP_VIEW` / `PRODUCT_VIEW` / `WHATSAPP_CLICK` rows for any shop. That makes every dashboard number attacker-controlled, and — because `createReview` gates on the presence of a `WHATSAPP_CLICK` row for that user (`reviews.ts:45-59`) — it makes the review gate a one-line bypass. The "only buyers who actually contacted this seller may review" guarantee does not hold.

**Inflated.** Every server render writes a view row. Measured:
```
5 × curl                    → +5 PRODUCT_VIEW rows
3 × curl (Googlebot UA)     → +3 PRODUCT_VIEW rows
```
No deduplication, no bot filtering, no session throttling. Since every shopper route renders dynamically (F-24), crawlers, link previews and page refreshes all count as views.

**Recommended fix** Rate-limit and origin-check `trackEvent` (or drop the public action and record views only from the server render path); filter known bot user-agents; deduplicate per session/IP within a window. For the review gate, verify the click server-side rather than trusting a row anyone can create.

## 4. Data integrity findings

**Where UI, API, database and cache agree** — and this is worth stating plainly, because it is most of the system:

- The 8-field update matrix showed **zero collateral damage**: changing price touched only `price` and `discountPercent`; changing description touched only `description`, and so on.
- Cascade deletes are correct. After deleting products and shops: 0 orphan `ProductImage`, 0 orphan `Wishlist`, and `Analytics.productId` correctly nulled by `onDelete: SetNull`.
- Unique constraints held under concurrent load. Three simultaneous creates with an identical title produced exactly one row.
- Pagination over 35 products across 5 pages produced no duplicates and no gaps.

**Where they disagree:**

| Layer boundary | Discrepancy |
|---|---|
| DB → UI | `Shop.averageRating` / `reviewCount` (denormalised) drive marketplace filters and creator cards, while store and product pages compute the average live from `shop.reviews`. The two can disagree; the denormalised pair is only recalculated inside `createReview`, never after a cascade delete of a user or review. |
| DB → UI | A shop with `reviewCount = 0` renders as `(100)` reviews and `⭐ 4.8` (F-01) — the UI asserts data the database does not contain. |
| API → DB | `price: "12abc"` enters the API as a string and lands in the database as `12`. The user's input and the stored value differ with no error. |
| API → DB | `category` accepts any string. The database can hold categories that no category page, filter or navigation surface will ever show. |
| DB → column | `discountPercent` is written on every create/update and carries a dedicated index (`@@index([status, discountPercent])`) but is **never read anywhere in the application**. It is also stored as a fraction (`0.5`) despite the name. |
| Client → API | `/api/cart/validate` never checks that a `productId` actually belongs to the submitted `shopId`, so a tampered cart can pair one seller's product with another's WhatsApp number. |
| Storage → DB | `updateProduct` and `deleteProduct` delete storage files **before** the database transaction. If the transaction rolls back (reproduced via an update/delete race), the rows survive but the files are gone — permanently broken images with no rollback path. |

## 5. Realtime findings

There is no realtime transport — no WebSocket, no SSE, no subscription. "Realtime" is `LiveRefresh`, a 60-second `router.refresh()` poll (`live-refresh.tsx:34`) that runs only while the tab is visible, plus an immediate refresh on `visibilitychange`.

**Measured** (production build, two tabs, one seller):

```
t=0    Tab A: All Products (15)   ← row inserted directly into the DB at t=0
t=10s  Tab A: All Products (15)
t=30s  Tab A: All Products (15)
t=50s  Tab A: All Products (15)
t=60s  Tab A: All Products (16)   ← converged
```

| Dimension | Result |
|---|---|
| Multi-tab | Converges, up to 60 s late |
| Tab focus | Refreshes immediately ✅ |
| Background tab | Correctly does not poll ✅ |
| Duplicate / out-of-order events | Not applicable — no event stream; each poll is a full re-render |
| Reconnect after network loss | Recovers on the next tick; nothing to resubscribe |
| Permanent staleness | None observed — the state always converged |

**Findings**
- **F-27 (P2)** The badge reads **"LIVE"** with a pulsing green dot. A seller watching an order come in will reasonably expect seconds, not a minute. Either relabel it (*"Updates every 60s"*) or make it real.
- **F-27b (P2, cost)** Every visible dashboard tab issues a full server re-render each minute, and `getShopAnalytics` runs **14 sequential `count()` queries** (a 7-day loop, two per day) plus the dashboard's own queries. Ten sellers with the tab open is ~150 queries/minute doing nothing. Collapse the loop into one `groupBy` with `date_trunc`.
- **F-30 (P3)** Analytics day buckets use server-local time. On Vercel that is UTC, so an IST seller's "today" is shifted by 5½ hours and the chart's last bar is always partial.

## 6. Product CRUD findings

**Create** — F-02, F-03, F-05, F-06, F-07, F-17, F-18. Slug collision handling is a check-then-insert loop (`products.ts:82-94`); the unique constraint saves correctness under concurrency, but the loser gets a raw Prisma exception instead of a retry (F-16). `quickAddProducts` builds slugs from `untitled-product-${Date.now()}-${idx}`, which collides if two quick-adds land in the same millisecond, and skips `ProductSchema` entirely — those drafts have `price: 0` and `category: 'Other'` with no validation.

**Read** — Correct and well-filtered. `status: 'ACTIVE'` plus `shop.isSuspended: false, isPaused: false` is applied consistently across the homepage, category pages, search and store pages. Suspended shops render an explicit notice. One inconsistency: a *paused* shop's product pages hard-`notFound()` while its store page renders an "away" notice.

**Update** — F-04 (lost update) is the important one. Also: every save runs `deleteMany` + `create` on the image set, so **`ProductImage` IDs change on every update**. Any client holding IDs for `reorderProductImages` will fail with "Unauthorized image update" after an unrelated save. Renaming a product changes its slug with no redirect, silently breaking every shared link and QR code (F-26).

**Delete** — Correct at the database level. Storage cleanup ordering is wrong (see §4). Second delete of the same id returns a raw Prisma error rather than "Product not found" (F-16).

**Media** — F-02, F-05, F-09, F-10, F-12. Upload validation itself is good: 5 MB cap, MIME allowlist, and magic-byte verification. Twenty identical image URLs on one product are accepted, as are negative `displayOrder` values and multiple `isPrimary: true` images.

**Validation** — Zod is applied consistently server-side and strips unknown fields (no mass assignment). The gaps are in the *rules*, not the plumbing: no trim, no category enum, no URL host allowlist, no `compareAtPrice > price` check, and a `parseFloat` preprocess that accepts junk (`"12abc"` → `12`).

## 7. Security findings

Only findings I verified are listed. **Product-level authorization is genuinely solid** — every IDOR probe (update, delete, stock toggle, create-in-another-shop, image-reorder ID swapping) was correctly rejected server-side, and unauthenticated calls return `Unauthenticated`. There is no stored XSS; no SQL injection (all raw SQL uses parameterised `Prisma.sql`); CSP and security headers are present.

| ID | Finding | Severity | Status |
|---|---|---|---|
| F-05 | SSRF via product image URL — outbound request to an arbitrary host observed | P1 | **Confirmed** |
| F-10 | Cross-tenant image deletion via attacker-controlled image URLs | P1 | Verified by code path |
| F-11 | Passwordless dev login functional in a production build; flag set in `.env.local` | P1 | **Confirmed** |
| F-14 | `trackEvent` is a public unauthenticated action → forgeable analytics + review-gate bypass | P1 | **Confirmed** |
| F-02 | Unvalidated image host → denial of service on shared public pages | P0 | **Confirmed** |
| F-16 | Raw Prisma errors returned to the client (file paths, query fragments, constraint names) | P2 | **Confirmed** |
| F-21 | `/api/cart/validate` is unauthenticated and returns title/price of DRAFT and ARCHIVED products plus the seller's raw WhatsApp number, with no product↔shop consistency check | P2 | **Confirmed** |
| F-22 | Role is read from the JWT and never re-checked against the database; an admin demotion does not take effect until the token expires | P2 | Verified by code path |
| F-06 | Unbounded image fetch — cheap resource-exhaustion vector | P1 | **Confirmed** |
| F-34 | `middleware.ts:4-15` interpolates a URL into inline HTML and JS without escaping | P3 | Not exploitable as tested — WHATWG URL encoding neutralises `"`, `<`, `>`. Fragile; escape it anyway. |

**Not found (tested):** stored/reflected XSS, SQL injection, mass assignment, product-CRUD IDOR, admin-route bypass, secrets in git history (`.env*` is correctly ignored; no tracked env files, no `.env` in history).

## 8. Recommended fixes, in priority order

**Before launch (P0/P1)**

1. **F-01** Remove every fabricated-social-proof fallback: `reviewCount || 100`, the hard-coded `⭐ 4.9 (124 reviews)`, and the production defaults in `demo.ts` (`4.8`, `'Mumbai'`, `'Verified Creator'`). Render nothing when there is nothing.
2. **F-02 + F-05** Restrict `ProductImageSchema.url` to `https:` and the hosts in `remotePatterns`; reject private/loopback/link-local. Add a per-card error boundary so one row can never take a shared page down.
3. **F-08** Wrap all nine server-action call sites in `try/catch/finally`. Highest reliability-per-line change in the report.
4. **F-03** Keep the submit button disabled through the success window.
5. **F-04** Add an `updatedAt` precondition to `updateProduct` and `updateShop`; tell the user when their write was rejected.
6. **F-07** Trim titles, reject blank ones, and make `slugify` produce something usable for non-Latin scripts.
7. **F-11** Gate `isDevLoginEnabled()` on `NODE_ENV !== 'production'`; confirm the flag is absent from every Vercel environment.
8. **F-06** Add a timeout and size cap to the image fetch; move theme extraction off the request path.
9. **F-09** Gate the Supabase mock branch on non-production; fail loudly on missing configuration.
10. **F-12** Declare `file-type` in `dependencies`; add an upload smoke test.
11. **F-13** Make `prisma/seed.ts` refuse any non-local database; repoint the local `.env`.
12. **F-10** Scope storage deletes to the caller's own objects.
13. **F-14** Rate-limit and origin-check `trackEvent`; verify the review gate server-side.

**Soon after (P2)**

14. **F-16** Map Prisma errors (`P2002`, `P2025`) to user-facing messages; never return `error.message` from a catch block.
15. **F-15** Remove `export const revalidate = 300` from the two store routes — it is inert (both render dynamically) and it is what turns `notFound()` into an HTTP 200 soft-404.

20. **F-21/F-22** Scope `cart/validate` to ACTIVE products and stop returning raw WhatsApp numbers pre-checkout; re-read role from the database in `verifyAdminAuth`.

**The distance from 5.5 to 8 is about a week.** None of the P0/P1 items require architectural change; the largest is adding an `updatedAt` precondition to two update paths. The architecture is sound — the gaps are in input validation, error handling, and one guardrail (demo data) that was built correctly and then bypassed by the pages it was meant to protect.
